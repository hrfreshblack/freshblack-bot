# Архітектура та логіка FreshBlack bot

> Джерело істини щодо бізнес-логіки бота. Написано HRD, звірено з кодом.
> Будь-яка зміна поведінки бота має спочатку оновити цей файл.

## 1. Загальна структура

Чотири частини:

1. **Telegram Bot** — інтерфейс, з яким працюють співробітники.
2. **Railway / server.js** — "мозок": кнопки, сценарії (офіс / виробництво / запити), нагадування.
3. **Postgres (Railway, `db.js`)** — робоча база бота. Усі перевірки (has_in/has_out, відсутність) і всі записи (checkin, заявки, виробничі звіти) читаються/пишуться сюди миттєво, без очікування Google. Це єдине джерело істини для *живої* поведінки бота "тут і зараз".
4. **Google Sheets + Apps Script Bridge** — дзеркало для людей. Отримує ті самі дані окремо, у фоні (черга `outbox` у Postgres, воркер `flushOutbox` у server.js) — не бере участі в жодному рішенні бота, лише накопичує історію для табеля/зарплати/перегляду. `employees` (імена, active) підтягуються з Таблиці в Postgres раз на 5 хв — це єдиний напрям, у якому Таблиця й досі "годує" бота.

Детальніше про причину і сам перехід — `docs/DEPLOYMENT.md`, розділ 6.

## 2. Таблиці (у Google Таблиці "Сводна по годинах")

### employees — база співробітників
Поля: `employee_id`, ПІБ, `telegram_chat_id`, `telegram_user_id`, статус активності.
Використання: старт через QR, ідентифікація, ранкові нагадування, резервний пошук chat_id.

### checkins — журнал входів/виходів
Поля: `timestamp`, `employee_id`, `telegram_user_id`, `telegram_chat_id`, `full_name`, `type` (in/out), `mode` (office/remote/production), `entry_type` (office/production), `work_format` (office/remote/production), `remote_reason`, `source`.
З цієї таблиці технічна таблиця і табель рахують робочий час.

### production_shift_log — виробничі звіти по станціях
Поля: `shift_id`, `opened_at`, `closed_at`, `employee_id`, `telegram_chat_id`, `telegram_user_id`, `full_name`, `station_name`, `result_text`, `source`.
Не "вхід/вихід", а звіт: хто, коли, по якій станції, який результат.

### timeoff_requests — заявки на відпустку/лікарняний
Поля: `request_id`, `employee_id`, `telegram_chat_id`, `telegram_user_id`, `full_name`, `request_type` (vacation/sick), `request_subtype` (annual/unpaid), `date_from`, `date_to`, `replacement_person`, `comment`, `status`, `status_hr`, `status_chief_acc`, `final_status`.

### (інші аркуші, не оброблюються поточним ботом)
`dashboard`, `worklog`, `ФІО QR` — існують у тій самій таблиці, наповнюються іншим Apps Script кодом (меню "FreshBlack HR"), який поки не переданий і не входить у зону змін.

### Окремі таблиці, що читають ці дані (не чіпаємо на цьому етапі)
- **"Табель робочого часу FRESH BLACK"** — помісячний табель по відділах.
- **"ЗП виробництво"** — розрахунок зарплати виробництва (норми/факт/втрати).

Логіка табеля: по `telegram_user_id`/`employee_id` і даті шукається перший `in` за день → `Start`, останній `out` за день → `End`. **Скрипт табеля не повинен**: перезаписувати ручні правки, чіпати формули, чистити комірки, змінювати `Diff`.

## 3. Запуск бота

`/start FB000123` → бот бере `employee_id` з QR → `get_employee` в Apps Script → якщо знайдено: записує `telegram_chat_id`/`telegram_user_id` через `upsert_employee_chat` → показує головне меню (Офіс / Виробництво / Подати запит).

## 4. Обмеження часу роботи (Київ)

- до 07:30 → «Я ще сплю 😴»
- після 23:00 → «Я стомився і сьогодні більше не працюю 🥱»
- після 00:00 → «Я солодко сплю чого і тобі бажаю 💤» **(за задумом окреме повідомлення; у коді зараз це покривається тим самим «Я ще сплю», бо 00:00–07:30 потрапляє в одну умову — треба уточнити з HRD, чи потрібне справді третє окреме повідомлення)**

У цей час робочі дії недоступні. Групові чати (погодження HRD/бухгалтер) під це обмеження не підпадають.

## 5. Логіка офісу

**Вхід:** перевірка — не у відпустці/лікарняному, немає сьогоднішнього `in`, немає сьогоднішнього `out` → вибір формату:
- **Офіс** → `checkins`: `type=in, mode=office, entry_type=office, work_format=office`
- **Віддалено** → питає причину → `checkins`: `type=in, mode=remote, entry_type=office, work_format=remote, remote_reason=...`

**Вихід:** перевірка — є `in`, немає `out` → `checkins`: `type=out, entry_type=office, work_format=...`

## 6. Логіка виробництва

**Початок зміни:** перевірка (не відсутній, немає `in`, немає `out`) → `checkins`: `type=in, mode=production, entry_type=production, work_format=production` + у сесії створюються `production_shift_id`, `production_opened_at`, порожній `production_entries`.

**Звіт по станціях (о 17:45):** бот показує перелік станцій (Автомат 1кг, Фотосепаратор, Ручне пакування, Замішування кави, Дріп станок, Збірка дріпів, Обсмажка, Комірник) → співробітник обирає станцію → вводить результат → результат тимчасово зберігається в сесії → «Додати ще станцію» / «Завершити введення станцій».

**Завершення зміни:** 1) один запит `production_shift` записує всі зібрані станції в `production_shift_log` (кілька рядків за раз, якщо кілька станцій); 2) окремий запис `type=out, entry_type=production` в `checkins`. Сесія очищається.

## 7. Нагадування (пн–пт, час Києва)

| Час | Дія |
|---|---|
| 08:30 | Перше нагадування почати день — усім активним без `in` (крім відсутніх) |
| 09:30 | Друге нагадування — тим, у кого досі немає `in` |
| 17:45 | Виробництву — список станцій для звіту, якщо є `in`, `entry_type=production`, немає `out` |
| 18:00 | Офісу — «Не забудь завершити день» + кнопка Вихід, якщо є `in`, `entry_type=office`, немає `out` |
| 19:30 | Повторне нагадування офісу, якщо `out` досі немає |

Перед кожним нагадуванням — перевірка `is_employee_absent_on_date`: якщо на цю дату є заявка в `timeoff_requests` зі статусом, який **не** `rejected` (тобто включно з ще не погодженою, `pending_hrd`/`pending_accountant`, і з `approved`) — співробітник вважається відсутнім і нагадування не надсилається. **Підтверджено: це навмисна поведінка** — заявка "знімає" нагадування одразу після подання, ще до погодження.

## 8. Відпустка / лікарняний

«Подати запит» → тип (Щорічна відпустка / За свій рахунок / Лікарняний) → період (`ДД.ММ.РРРР - ДД.ММ.РРРР`) → для відпустки: хто заміняє; для лікарняного: коментар/причина → створення запису в `timeoff_requests` зі статусом `pending_hrd` → повідомлення в чат погодження → **HRD** погоджує/відхиляє → якщо погоджено, статус `pending_accountant`, повідомлення **бухгалтеру** → бухгалтер погоджує/відхиляє → фінальний статус `approved`/`rejected`.

## 9. Захист від дублювання

- Перед `in`: перевірка `get_daily_checkin_status` (`has_in`).
- Перед `out`: перевірка `has_out`.
- Антидубль кнопок: у сесії `_last_action` + `_last_action_ts`, повтор того самого натискання протягом короткого часу ігнорується.

## 10. Принцип навантаження на Google Sheets (історія; з появою Postgres втратило гостроту, але лишається орієнтиром)

Раніше кожна дія й перевірка йшли прямо в Apps Script — це й було головним джерелом гальмування бота. Тепер живі дії/перевірки йдуть у Postgres, а Таблиця отримує дані пізніше, чергою (`outbox`, батчами по 20 записів раз на 5 сек) — тож масового навантаження на Sheets в моменти пік більше немає за визначенням. Принцип "не писати/читати дрібно, накопичувати і йти одним запитом" лишається хорошим орієнтиром для самого outbox-воркера й для періодичної синхронізації employees, якщо колись знадобиться далі оптимізувати.

## 11. Відомі ризики (зі слів HRD + підтверджено кодом)

1. **Apps Script timeout** — при частих зверненнях або читанні багатьох рядків.
2. **Застарілий Apps Script URL** після нового розгортання → бот отримує HTML замість JSON.
3. **Порожній/неправильний `telegram_chat_id`** → бот не може написати співробітнику.
4. **(Закрито)** Раніше розмовний стан (сесії, стан планувальника нагадувань) зберігався у файлах на диску Railway, який не постійний — будь-який деплой стирав його, і людям треба було заново відкривати бота через QR. Тепер обидва зберігаються в Postgres і переживають будь-який деплой/рестарт без винятків.
5. **Ручна зміна назв колонок** у таблицях ламає bridge.
6. **Ручна зміна `telegram_chat_id`/`telegram_user_id` прямо в Таблиці** тепер ні на що не впливає — цими полями керує лише Postgres, Таблиця в цій частині лише для перегляду (див. розділ 1).

## 12. Заплановано, ще не реалізовано: модуль Комірник / склад

Окремий сценарій для станції "Комірник": вибір SKU зі списку → вказати актуальний залишок → «додати ще продукт?» → пакетний запис.

Нова вкладка `warehouse_stock_log`: `timestamp`, `employee_id`, `telegram_user_id`, `telegram_chat_id`, `full_name`, `sku_name`, `sku_format`, `stock_qty`, `source`.

Друга вкладка `stock_current`: останній залишок по кожному SKU, критичний мінімум, статус (OK / низький запас / критично), підсвітка для виробництва.

**Важливо:** цей модуль не змішувати з `production_shift_log` — це складський облік, а не виробничий звіт. Зараз станція "Комірник" у боті працює як звичайна станція з довільним текстом — це тимчасово, до впровадження окремого сценарію.

## 13. Наскрізний потік

QR → ідентифікація по `employee_id` → запис Telegram ID в `employees` → вибір напряму (офіс/виробництво/запит) → офіс: `in` → `out`; виробництво: `in` → звіт по станціях → `production_shift_log` → `out`; запит: заявка → погодження HRD → погодження бухгалтера → нагадування працюють автоматично за розкладом → табель рахує години з `checkins` → виробничі звіти зберігаються окремо → (у майбутньому) складський модуль рахує залишки окремо.
